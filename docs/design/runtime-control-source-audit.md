# Scoped runtime controls: source audit

Evidence supporting proposed [ADR-051](../adr/051-runtime-halt.md). No controls or parameter choices described by the ADR have been implemented or tested by this audit.

A check of a plain control table inside `claim_ready_runtime` is a plausible enforcement point for queue-storage runtime claims, but is not a complete dispatch halt. Canonical dispatch bypasses that function on both audited branches; main also has callable per-slot claim functions. A database read can avoid a client polling interval, but does not establish a barrier against claims already in progress or handler launches after the halt commits.

This source audit pins main to [`d16ef5c4572cb96b25a8f26ad85bd5915ab76f64`](https://github.com/hardbyte/awa/commit/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64) and `release/0.6.x` to [`8cec9e45a45735c300a89c98dc96573589100386`](https://github.com/hardbyte/awa/commit/8cec9e45a45735c300a89c98dc96573589100386). It inspects source, not a running halt implementation or a mixed-version rehearsal. The prospective patch examples below are separate commits, not evidence that the pinned release contains their behavior.

## Claim routes

- **Canonical storage bypasses the proposed check.** The dispatcher embeds a `WITH claimed … UPDATE awa.jobs_hot SET state = 'running'` query. Its predicate checks queue pause, with no call to `claim_ready_runtime`. This exists on [main, `awa-worker/src/dispatcher.rs:745–795`](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/dispatcher.rs#L745-L795) and [0.6, lines 563–612](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-worker/src/dispatcher.rs#L563-L612). Main explicitly selects canonical storage for canonical-drain runtimes and can fall back to it when auto-finalization does not succeed: [client.rs:1529–1605](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/client.rs#L1529-L1605). Guarding only the queue-storage function leaves these workers outside the halt boundary, including old binaries executing the embedded query.
- **The audited queue-storage runtime APIs converge on the SQL wrapper.** `claim_batch`, `claim_runtime_batch_with_aging`, its instance-gated wrapper, and `claim_job_batch` reach `claim_ready_rows_tx`, which issues `FROM {schema}.claim_ready_runtime($1, $2, $3, $4)`. See [main, queue_storage.rs:5261–5309](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L5261-L5309), [7161–7306](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L7161-L7306), [7731–7828](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L7731-L7828), and [0.6, 3575–3623](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/queue_storage.rs#L3575-L3623), [5172–5310](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/queue_storage.rs#L5172-L5310). No separate Rust-generated new compact-claim INSERT was found in these pinned runtime paths. The Rust INSERT into `lease_claims` during schema preparation copies existing legacy claims; it is not new dispatch: [main, 4339–4357](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L4339-L4357).
- **Receipt mode changes the write target, not the runtime entry point.** On 0.6, receipts use compact `lease_claim_batches` for zero deadlines and row-based `lease_claims` for positive deadlines; legacy mode writes `leases`: [v023:2684–2689](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/migrations/v023_install_queue_storage_substrate.sql#L2684-L2689). Main uses compact batches for both receipt deadline modes and retains legacy `leases`: [v023:3282–3294](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v023_install_queue_storage_substrate.sql#L3282-L3294). A guard must precede every claim-producing arm, not only a `leases` write.
- **Main has a lower SQL entry point.** The wrapper dynamically invokes `claim_ready_slot_N`: [v023:4155–4175](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v023_install_queue_storage_substrate.sql#L4155-L4175). Those functions independently select ready rows and execute the claim CTE: [4241–4254](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v023_install_queue_storage_substrate.sql#L4241-L4254), [4291–4357](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v023_install_queue_storage_substrate.sql#L4291-L4357). A permitted direct slot caller bypasses a wrapper-only check. Source inspection found no such Rust runtime caller at the pinned commits; permissions and external SQL callers remain part of the enforcement proof.

## What the database check can guarantee

A fresh per-claim read can reject claims without waiting for a runtime control polling loop. Describe this as **no additional client polling interval on covered claim paths**, not instantaneous fleet cessation. PostgreSQL Read Committed reads committed data at query snapshot time; Repeatable Read retains its transaction snapshot. A claim that read permission before a concurrent halt committed can still write and commit afterward. A plain read of the control row creates no serialization barrier with the halt writer. Serializable ordering alone also does not require overlapping claims to be ordered after the halt. These are consequences of [PostgreSQL transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html), not behavior verified for an implemented halt.

The current SQL functions default to `VOLATILE`; PostgreSQL documents fresh snapshots for queries inside volatile functions. An entry check followed by later SQL therefore still leaves an inter-statement race; moving the check into a claim statement still leaves claims whose statement snapshot predates the halt. Prepared statements do not themselves freeze table values, but a wrongly declared `IMMUTABLE` control helper can cache stale results: [function volatility](https://www.postgresql.org/docs/17/xfunc-volatility.html). ADR-051 requires Read Committed claim transactions, rejects other isolation levels, and treats overlapping evaluations as outstanding work until they settle. These are implementation obligations, including databases configured with a different default isolation level.

Claims commit before the runtime returns jobs for execution, and dispatch later spawns handlers: [main, queue_storage.rs:7327–7356](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L7327-L7356), [dispatcher.rs:929–946](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/dispatcher.rs#L929-L946). A database claim guard alone cannot prevent a previously claimed job from launching after halt, cancel an executing handler, or stop maintenance and cron. Replacing a compatible SQL function can constrain older binaries that still call it; it does not constrain their other SQL paths or add runtime control observation.

## Custom schemas and 0.6 delivery

Every installed queue-storage schema owns a wrapper and its claim representation. Main's v051 refresh discovers trusted substrates, preserves their slot counts and receipt mode, then reinstalls them: [v051:25–91](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v051_claim_slot_functions.sql#L25-L91). The discovery bootstrap rejects unsafe configured schemas and warns about skipped untrusted schemas: [queue_storage_schema_discovery.sql:202–243](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/queue_storage_schema_discovery.sql#L202-L243). Updating only `awa.claim_ready_runtime` cannot establish coverage for custom schemas. New installs, later `prepare_schema` calls, migrations, and restores must preserve the guard; preparation invokes the installer again: [queue_storage.rs:4243–4257](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L4243-L4257).

The pinned 0.6 release has versioned migrations through v040 and skips already-applied versions; it has no schema-patch registry in that migration runner: [migrations.rs:172–187](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/migrations.rs#L172-L187), [281–300](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/migrations.rs#L281-L300). Editing an old migration alone would not update an existing v040 database.

Prospective commit [`b5016b7d`, migrations.rs:233–249](https://github.com/hardbyte/awa/blob/b5016b7db3e5f0c2294af840557ebd990803d17d/awa-model/src/migrations.rs#L233-L249) provides versionless, probed schema patches because 0.7 owns v041 onward. Its `definer_lane_provisioning` patch composes updated installer definitions with a custom-schema sweep: [410–423](https://github.com/hardbyte/awa/blob/b5016b7db3e5f0c2294af840557ebd990803d17d/awa-model/src/migrations.rs#L410-L423). It preserves old helper arguments and cursor semantics, exports repeatable SQL, and needs ownership-capable migration credentials: [patch:21–27](https://github.com/hardbyte/awa/blob/b5016b7db3e5f0c2294af840557ebd990803d17d/awa-model/migrations/patches/definer_lane_provisioning.sql#L21-L27). Its function-only lock profile does not transfer to a halt patch that creates a table or refreshes the whole substrate. Main explicitly warns that substrate reinstallation can hold table locks through commit: [v051:17–22](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/migrations/v051_claim_slot_functions.sql#L17-L22).

Separate prospective commit [`54f0bc6a`, migrations.rs:233–253](https://github.com/hardbyte/awa/blob/54f0bc6a5479f1e769514af1d742826d48aba1db/awa-model/src/migrations.rs#L233-L253) adds an `awa.schema_patches` ledger, with probe backfill and no application on newer schemas. It is a delivery example, not a merged prerequisite or halt implementation. A 0.6 backport appears technically possible through additive, versionless delivery, but requires branch-specific SQL, compatible return shapes, complete schema discovery, privileges, replay behavior, and a later-main migration that preserves the same boundary.

## Maintenance observation and reclamation

The leader holds a dedicated checked-out pool connection for its session advisory lock, while maintenance operations acquire other pool connections. The existing liveness `SELECT 1` runs every 30 seconds in the same `tokio::select!` loop as maintenance. Each selected branch awaits its work inline, so a blocked branch delays that check and cancellation. Initial cron synchronization also precedes the select loop and launches a separate cron evaluator. See [main maintenance.rs:1002–1133](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/maintenance.rs#L1002-L1133), [1254–1299](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/maintenance.rs#L1254-L1299), and [0.6:893–1065](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-worker/src/maintenance.rs#L893-L1065).

Replacing that inline query with a controls read alone cannot bound observation latency. ADR-051 instead proposes independently scheduled ownership of the same leader connection, serializing reads and advisory-lock operations. It adds no observer connection, but requires restructuring task ownership. Before admitting initial cron or maintenance work, the observer must have read the relevant controls. No elapsed-time observation bound proves that an already admitted database operation has stopped.

Queue, lease and claim timers each combine rotation with pruning. A `maintenance.prune` gate must cover both stages, not just calls named `prune_oldest*`. Terminal-count rollup independently acquires `ACCESS EXCLUSIVE` and truncates delta children, so it belongs behind the same gate. Main's rollup wrapper also folds prune deltas, trims rotation ledgers and considers automatic storage-authority changes. See [maintenance.rs:1206–1252](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/maintenance.rs#L1206-L1252), [1411–1476](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/maintenance.rs#L1411-L1476), [queue_storage.rs:18607–18635](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L18607-L18635), and [0.6:13924–13960](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/queue_storage.rs#L13924-L13960). PostgreSQL documents that [`TRUNCATE` acquires an exclusive table lock](https://www.postgresql.org/docs/17/sql-truncate.html#SQL-TRUNCATE-NOTES).

Both branches default prune lock timeout to 10 ms. This limits a particular lock wait, not the whole maintenance operation: preliminary singleton/slot row locks and prechecks can occur before the timeout is installed. The 0.6 setter is hidden and has no worker-builder, CLI or Python wiring at the audited baseline. Existing blocked/active backoff does not pace successful reclamation after resume. See [main default](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-model/src/queue_storage.rs#L49), [0.6 setter](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/queue_storage.rs#L2338-L2346), [prechecks and later lock timeout](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-model/src/queue_storage.rs#L14090-L14173), and [0.6 backoff](https://github.com/hardbyte/awa/blob/8cec9e45a45735c300a89c98dc96573589100386/awa-worker/src/maintenance.rs#L420-L485).

The five named scopes do not exhaust today's leader branches. Cleanup includes completed jobs, DLQ rows, batch operations, runtime snapshots and descriptors; other branches refresh queue health, dirty keys, metadata and priority aging or execute administrative batches. These must be mapped explicitly or stopped by the full-halt aggregate. Only control observation, liveness and admitted-work completion are exempt. See [main maintenance.rs:1136–1210](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/maintenance.rs#L1136-L1210).

## Observation and authority

Runtime snapshots default to 10 seconds and run on an independent reporter with delayed missed ticks. That reporter also publishes descriptors and cron reconciliation evidence, so continued control reporting during a halt must not silently continue halted application work. Snapshot age is not control-observation age; publish actual observed revisions and monotonic ages, and distinguish draining, cancellation requested, quiescent and unknown. See [default interval](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/client.rs#L235), [cron reconciliation](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/client.rs#L2546-L2570), [descriptor publication](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/client.rs#L2748-L2762), and [reporter loop](https://github.com/hardbyte/awa/blob/d16ef5c4572cb96b25a8f26ad85bd5915ab76f64/awa-worker/src/client.rs#L2834-L2847).

The proposed cancellation contract adds a durable participant registry, not a new claim-path write per job. Registration must commit before a runtime admits work and serialize with control changes; the cancel transaction must record pending owner evidence before signaling cancellation. A compatible implementation can use the rare startup/control-change path for this interlock rather than lock a shared control row on every claim. Old unregistered runtimes require an enforced boundary before fleet coverage can be claimed. Missing snapshots, failed observation and expired heartbeats do not delete pending evidence. No such interlock or resolution implementation has been validated here.

Control-specific privileges are a proposed addition. Current documented roles include a broad combined `awa_runtime` principal; an operator-only command must revoke direct control-table writes from that role as well as producers, remove default `PUBLIC EXECUTE`, constrain the definer owner's privileges and fix its search path. [ADR-043](../adr/043-postgresql-capability-functions.md) proposes the capability direction; [PostgreSQL's definer-function guidance](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY) explains why merely marking a function `SECURITY DEFINER` is insufficient.

## Independently useful subset

A durable `maintenance.prune` switch with drain-only behavior can suppress new rotation, prune, retention and rollup admissions without changing claim SQL or introducing handler-cancellation reconciliation. It still needs initial and independent control observation, operator-only halt/resume, stale-state behavior, truthful acknowledgment and a shared reclamation budget. An unsupported scope must be rejected rather than recorded as enforced. Existing or returning leaders that ignore the switch remain outside its guarantee until upgraded or fenced. This subset is not a fleet-wide dispatch halt or a substitute for the later coverage proofs.

## Proof still needed

- Enumerate supported binary versions and actual claim SQL, including canonical drains, fallback selection, direct slot calls, receipt modes, custom schemas, and external callers. Exercise released old binaries against the patched database.
- Test concurrent halt/claim/launch under Read Committed, including blocked statements, delayed commits, rollbacks, prepared statements and multiple physical queue stripes. Refuse Repeatable Read and Serializable claim calls. Include in-flight claim evaluations and SQL in outstanding-work accounting before reporting drained.
- Verify least-privilege access to the control table, operator-only changes, producer access, and resistance to guard loss through schema preparation, upgrade, restore or a skipped custom substrate.
- Rehearse patch-first and binary-first rollout on 0.6 and main, external repeatable SQL, partial failures, subsequent migration, and actual lock duration under live traffic. Keep claim rejection evidence distinct from handler, cron and maintenance cessation.
- Hold a maintenance SQL operation or exhaust the worker pool while observing controls on the already-held leader session. Exercise startup, disconnect, leadership handoff, missing/malformed rows and monotonic freshness expiry. Confirm no replacement observer connection is required per poll.
- Check every reclamation entry point, reporter side effect and auxiliary leader branch against its scope or full-halt rule. Measure claim read overhead and maintenance availability before accepting the proposed timing defaults.
- Exercise resume with large backlogs across queue, lease, claim and terminal-delta rings and custom substrates; enforce one shared admission budget, ordinary cadences and backoff without catch-up. Verify cancellation uncertainty survives runtime-snapshot expiry and requires an audited reconciliation or fencing assertion before resumption.
